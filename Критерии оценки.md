# Критерии оценки ответов модели

## Контекст

Модель обучается на задаче преобразования краткого пользовательского запроса в структурированную задачу.
Входные данные: короткое намерение пользователя (1–7 слов).
Ожидаемый выход: валидный JSON с тремя полями — `Задача`, `Дата`, `Рекомендация`.

---

## 1. Формат ответа

| Критерий | Ожидание | Ошибка |
|----------|----------|--------|
| Только JSON | Ответ содержит исключительно JSON-объект, без markdown, пояснений, преамбулы | Наличие текста вне JSON, обёртка в ` ```json ``` ` |
| Валидный JSON | Парсится без ошибок | Синтаксические ошибки, незакрытые скобки |
| Три обязательных поля | `Задача`, `Дата`, `Рекомендация` — все присутствуют | Отсутствие хотя бы одного поля |
| Названия полей | Точное написание с заглавной буквы на русском | `задача`, `task`, `Task`, `ЗАДАЧА` |

---

## 2. Поле «Задача»

| Критерий | Ожидание | Пример из датасета |
|----------|----------|--------------------|
| Начинается с глагола в инфинитиве | Позвонить / Написать / Запланировать / Подготовить | «Позвонить Иванову по текущим вопросам» |
| Конкретизирует намерение | Расширяет краткий запрос, добавляет контекст | «Набрать Иванову» → «Позвонить Иванову по текущим вопросам» |
| Не дублирует запрос дословно | Формулировка отличается от входа, содержит уточнение | «Письмо команде» → «Написать письмо команде проекта с важной для них информацией» |
| Длина | 5–15 слов | — |
| Отсутствие дат внутри задачи | Дата выносится в отдельное поле | «Позвонить до конца дня» — неверно |

---

## 3. Поле «Дата»

Датасет использует два допустимых формата:

| Ситуация | Ожидаемое значение | Примеры из датасета |
|----------|--------------------|---------------------|
| Пользователь указал дату явно («сегодня», «до конца дня», конкретная дата) | `DD.MM.YYYY` — вычисленная дата | «Набрать Иванову» → `21.04.2026`; «Согласовать документы до конца дня» → `21.04.2026` |
| Дата не указана или указана расплывчато («на неделе», «завтра», «потом») | `{дата в формате DD.MM.YYYY}` — плейсхолдер | «Провести совещание по проекту завтра» → плейсхолдер; «На неделе разобрать почту» → плейсхолдер |

**Ошибки в поле Дата:**
- Неверный формат: `2026-04-21`, `21/04/2026`, `April 21`
- Произвольный текст вместо даты или плейсхолдера
- Конкретная дата там, где должен быть плейсхолдер (и наоборот)
- Плейсхолдер с опечаткой или изменённым текстом

---

## 4. Поле «Рекомендация»

| Критерий | Ожидание | Пример |
|----------|----------|--------|
| Практичность | Содержит конкретный совет, а не общую фразу | «Перед звонком подготовить вопросы для обсуждения» — да; «Выполните задачу качественно» — нет |
| Связь с задачей | Совет относится именно к данной задаче, а не к другой | Для задачи «Написать письмо» — совет про письмо, не про звонок |
| Длина | 8–20 слов | — |
| Без повторения задачи | Не пересказывает поле `Задача` | — |
| Форма глагола | Инфинитив или повелительное наклонение | «Подготовить список вопросов» / «Проверь данные» |

---

## 5. Устойчивость к вариациям входа

Оценивается на eval-датасете (`dataset-eval.jsonl`), где системные промпты варьируются:

| Системный промпт | Ожидание |
|-----------------|----------|
| «Ты - помощник в постановке задач» | Стандартный ответ |
| «Ты - помощник в формулировании задач» | Тот же формат |
| «Ты - личный помощник для планирования задач» | Тот же формат |
| «Ты - ассистент по планированию» | Тот же формат |
| «Ты - помощник по планированию и формулированию задач» | Тот же формат |

Модель не должна менять структуру ответа при смене системного промпта — формат JSON и логика заполнения полей остаётся одинаковой.

---

## 6. Шкала оценки (для ручной проверки)

| Балл | Описание |
|------|----------|
| **3** | Все поля корректны: JSON валиден, Задача начинается с глагола и конкретизирует запрос, Дата в правильном формате, Рекомендация практична и по теме |
| **2** | Один незначительный недостаток: небольшая неточность в формулировке, но смысл верный; или рекомендация слишком общая |
| **1** | Грубая ошибка в одном поле: неверный формат Даты, Задача дублирует запрос без конкретизации, или Рекомендация не по теме |
| **0** | Невалидный JSON, отсутствующие поля, или ответ не в JSON-формате |

---

## 7. Автоматические проверки (для EvalRunner)

Реализуются как структурные проверки без участия модели-судьи:

- [ ] `json.parse(response)` — не бросает исключение
- [ ] Наличие ключей `Задача`, `Дата`, `Рекомендация`
- [ ] `Задача.length >= 10`
- [ ] `Рекомендация.length >= 10`
- [ ] `Дата` соответствует `\d{2}\.\d{2}\.\d{4}` или `\{[^}]*дата[^}]*\}`
- [ ] `Задача` не совпадает с `userInput` дословно (нормализованное сравнение)
